## Review and History Contract

### Primary Screens
- Add three connected surfaces in the existing shell: `Import history`, `Batch detail`, and `Review queue`.
- Keep all three inside the current app-shell chrome. Do not open review work in modal-only flows or detached utility windows.
- Use batch context as the top-level organizing principle everywhere unresolved work appears.
- Review queue shows unresolved items only. Resolved history belongs in batch detail and audit later, not mixed into the active queue.

### Import History List
- Import history is the operational ledger for import attempts, not an analytics table.
- Each history row must show: import date and time, account label, file count, accepted transaction count, blocked duplicate count, unresolved review count, and a status badge.
- Show all attempt outcomes in one list: `Imported`, `Needs review`, `Rejected`, and `Failed`.
- Default sort is newest first.
- Use one row per batch or attempt, with the full row clickable to open batch detail.
- Reserve a right-aligned re-entry action for batches with unresolved work: `Open review queue`.
- Use concise filters only if needed for this phase: status filter and search by batch label or filename. Do not expand into ledger-style faceted search.

### Batch Detail
- Batch detail is the receipt view for one import attempt.
- Structure the page in three vertical sections: summary strip, per-file outcomes, transaction-level drill-down.
- Summary strip must restate current batch status, accepted count, blocked duplicates, unresolved review count, and last updated time.
- Per-file outcomes stay grouped by source file so the owner can inspect what happened without losing file context.
- Transaction-level drill-down is read-only in this phase except for entry into review actions.
- If unresolved items exist, batch detail must surface a persistent primary action: `Review unresolved items`.
- If all items are resolved, batch detail must remove warning emphasis and show the final imported state.

### Review Queue
- Review queue is a financial operations inbox, grouped by batch first and issue cards second.
- The primary visual anchor of the review queue is the active batch group header with its unresolved count and progress phrase. This element should draw the eye first before individual issue cards.
- Each batch group header must show the batch label, current status badge, unresolved count, and a progress phrase such as `3 of 7 resolved`.
- Inside a batch group, sort blocking items before warning items.
- Within each severity group, keep issue cards in source-file order when possible.
- Each review card must show: issue type label, severity label, source file or row context, short explanation, protected fields, and allowed actions.
- Use one expanded detail panel at a time on smaller widths; on wide desktop layouts, support a split view with the item list on the left and active detail panel on the right.
- Review queue must support partial completion across sessions. Do not imply a finish-in-one-sitting workflow.

### Resolution Actions
- Single-item actions: `Accept as-is`, `Edit before accepting`, `Mark as duplicate`, `Mark as not duplicate`, `Discard row`, `Apply tag`.
- Bulk actions allowed only for the locked Phase 3 set: accept selected as-is, discard selected, mark selected as duplicate, mark selected as not duplicate, and apply a tag to selected.
- Bulk-action controls remain disabled until at least one eligible item is selected.
- Editing before acceptance is limited to date, description, reference ID, and tags.
- Amount and running balance must render as protected read-only fields with muted styling and helper copy explaining why they cannot be edited here.
- Every destructive or trust-sensitive action must offer a persisted undo or restore path after completion.

### Navigation and Re-entry
- Provide direct re-entry into review from both import history and batch detail.
- Keep the current import workspace handoff intact: after an import completes with unresolved warning-level items, the owner can continue now or leave and return later.
- Preserve batch context during navigation. If the owner opens review from a batch row, start in that batch group rather than a generic global top state.
- Include a visible return path from review queue back to import history.
- In `Import history`, the eye should land first on the batch status and unresolved review count so the owner can immediately identify which imports still need intervention.
- In `Review queue`, the eye should land first on the active batch header and unresolved-progress area so the owner understands source context before acting on any row.

## State and Feedback Contract

### Status Language
- Use four canonical batch statuses only in this phase: `Imported`, `Needs review`, `Rejected`, `Failed`.
- `Needs review` is the active caution state for any batch with unresolved items.
- Use severity labels on review items: `Blocking` and `Warning`.
- Blocking items must visually read as stop-work issues; warning items must read as review-soon issues, not failures.

### Live Updates
- Import history counts and batch-detail counters must refresh immediately after a review mutation completes.
- Live update means authoritative refetch after mutation, not speculative background syncing.
- After resolving an item, remove it from the unresolved queue immediately and update the batch progress phrase.
- If the last unresolved item is resolved, the batch status changes from `Needs review` to `Imported` in the same refresh cycle.

### Empty States
- Import history empty state heading: `No imports yet`
- Import history empty state body: `Import an ICICI statement to create your first batch history entry and review trail.`
- Review queue empty state heading: `No unresolved review items`
- Review queue empty state body: `All current import issues have been resolved. You can return to import history or import another statement batch.`
- Batch detail empty drill-down state should say that no reviewable rows remain rather than implying data loss.

### Error and Recovery States
- Review mutation error copy must explain that the action was not saved and the current queue remains unchanged.
- Failed batch detail must show the reason summary first, then available next steps.
- Rejected file outcomes must remain inspectable from history and batch detail.
- Undo or restore feedback must confirm exactly what was reversed, such as `Duplicate mark removed` or `Discard restored to review queue`.
- Do not use ephemeral toast-only recovery for destructive actions. A visible inline restore affordance or persistent notification region is required.

### Confirmation Rules
- `Discard row` requires explicit confirmation naming the row will be removed from acceptance and can be restored.
- `Mark as duplicate` requires confirmation only when triggered in bulk; single-item duplicate marking may use immediate action plus undo.
- `Accept as-is` and `Mark as not duplicate` do not require a blocking confirmation.
- `Apply tag` never requires destructive confirmation.

### Keyboard Contract
- `Tab` and `Shift+Tab` traverse batch groups, row selection controls, primary actions, and detail-panel fields in visual order.
- `Enter` triggers the focused primary action for the active review card when validation passes.
- `Esc` closes the active detail panel or restore banner without leaving the current screen.
- Batch headers and unresolved-item cards must be reachable and operable by keyboard.
- After a review action completes, focus moves to the next unresolved item in the same batch when available; otherwise it returns to the batch header.

## Component Inventory

- `Import history table or list`: batch rows, status badge, count columns, reopen-review action.
- `Status badge`: imported, needs review, rejected, failed, blocking, warning.
- `Batch summary strip`: counts, account, timestamps, current state.
- `Per-file outcome card`: file identity, outcome, reason snippet, drill-down entry.
- `Review batch group`: grouped unresolved section with progress and batch metadata.
- `Review item card`: issue summary, severity, row context, allowed actions, selection control.
- `Review detail panel`: read-only protected fields, editable safe fields, supporting rationale.
- `Bulk action bar`: selected count, safe bulk actions, clear selection.
- `Undo or restore banner`: explicit reversible-action feedback with restore action.

Use the established Phase 1 and Phase 2 card language: large rounded surfaces, muted secondary fills, restrained accent emphasis, and strong scan order over decorative density.

| Token | Value | Usage |
|-------|-------|-------|

| sm | 8px | Compact metadata rows, helper text, chip spacing |
| md | 16px | Default control spacing, row internals, card content rhythm |
| lg | 24px | Card padding, batch-group padding, detail-panel sections |
| xl | 32px | Main layout gutters, history-to-detail spacing |
| 2xl | 48px | Separation between major page regions and empty states |
| 3xl | 64px | Top-level page breathing room inside the shell |

Exceptions: 44px minimum hit area for row selection controls, header actions, and tertiary icon-only actions; 56px minimum height for primary CTA buttons and bulk-action confirmation buttons

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 600 | 1.4 |
| Heading | 20px | 600 | 1.2 |

Use sentence case throughout. Reserve display text for the page heading of import history and the top-level heading of a focused review screen only. Batch labels and row titles use body size with semibold emphasis rather than creating a fifth type scale.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | #F5F1E8 | App background, history canvas, review canvas, detail background |
| Secondary (30%) | #E2D7C5 | Batch cards, detail panels, grouped file outcomes, filter or action rails |
| Accent (10%) | #0F766E | Primary review actions, active row outline, progress indicators, selected states, restore affordances |
| Destructive | #B42318 | Discard confirmations, failed batch emphasis, irreversible warning copy |

Accent reserved for: `Open review queue`, `Review unresolved items`, `Accept as-is`, selected row states, active batch progress text, focus rings, and restore actions. Do not use accent for rejected or failed states, passive metadata labels, or decorative separators.

Use neutral ink and muted text from the existing token system for all non-critical metadata. Blocking vs warning distinction should rely on badge treatment and destructive or muted contrast, not additional brand colors outside the existing tokens.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Review unresolved items |
| Empty state heading | No unresolved review items |
| Empty state body | All current import issues have been resolved. Return to import history or import another statement batch when you're ready. |
| Error state | This review action could not be saved. Check the batch details, try again, and confirm the item is still unresolved before making another change. |
| Destructive confirmation | Discard row: This row will stay out of accepted transactions for this batch, but you can restore it from the review recovery prompt if this was a mistake. Continue? |

Microcopy rules:
- Lead with trust and traceability. Prefer `review`, `resolve`, `restore`, `batch`, `not saved`, and `available later`.
- Status labels must be operational, not emotional. Use `Needs review`, not `Attention needed` or `Urgent`.
- Protected-field helper copy must explain the reason: `Amount and running balance stay locked here to protect statement trust.`
- Avoid hype language such as `smart`, `magic`, `auto-cleaned`, or `fixed for you`.
