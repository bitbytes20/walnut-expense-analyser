## Shell and Flow Contract

### App Shell
- Use a two-layer shell from the first frame: branded application chrome plus centered task surface.
- Keep onboarding and lock states inside the same product shell language as later finance screens; do not switch to a generic modal or utility look.
- Use a desktop-first max content width of 1120px for onboarding surfaces, with the active panel capped at 560px for readable form work.
- Reserve the left or top shell region for brand presence only; Phase 1 does not expose navigation beyond `Lock now`.

### Onboarding Flow
- Use a linear wizard with `Back` and `Next`; do not show a numbered stepper.
- Follow the fixed order from context: Welcome, Household profile, PIN setup, Recovery key, Account profile, Finish.
- Show progress as plain language such as `Step 2 of 6` in the panel header, not as clickable milestones.
- Persist draft progress after every successful step transition so restart resumes at the last incomplete step.
- Place primary actions bottom-right and secondary actions bottom-left on every step.
- Use one primary task per screen; do not combine PIN creation and recovery-key work on the same view.

### Lock and Unlock
- Lock screen layout uses three zones: brand header, account context card, unlock panel.
- Surface household/app name, last active account label, and current theme styling on the lock screen.
- Place `Restore from backup` and `Use recovery key` as tertiary text buttons under the PIN form, visually separated from the primary unlock action.
- Include a persistent `Lock now` action in the desktop shell header once onboarding is complete.
- Do not show remaining-attempt counters. Show cooldown messaging only once backoff activates.

### Recovery Key
- Present the generated recovery key in two synchronized formats: segmented code block and word-list block.
- Put copy and download actions adjacent to the recovery key, above the confirmation control.
- Gate progression with an explicit confirmation control that remains disabled until the owner completes copy or download.
- Recovery-key reset flow later must use the same visual language as onboarding but open as a dedicated recovery task, not as an inline settings field.

### Account Profile Setup
- Bank field is fixed to `ICICI` and visually read-only.
- Required inputs: account display name, account holder name, base currency.
- Optional inputs: masked account number or nickname, opening balance metadata.
- If account setup is skipped, show a clearly labeled `Skip for now` secondary action and explain that the profile can be created from the first import later.

## State and Feedback Contract

### Validation
- Validate inline, on blur and on submit.
- Use field-level error text below the control, in plain language, without toast-only validation.
- PIN requirements must be visible before entry: minimum 6 digits, numeric only, confirmation must match.

### Loading and Save Feedback
- Use button-level loading states for `Next`, `Unlock`, `Finish`, and recovery actions.
- Use optimistic progress save only for wizard-step persistence; show a subtle `Progress saved on this device` helper line in the footer area.
- Do not use blocking full-screen spinners during onboarding resume; restore directly into the saved step.

### Empty and Success States
- First post-onboarding dashboard state must be an empty dashboard canvas with one import-oriented primary CTA.
- Recovery-key confirmation success should use inline confirmation, not a celebratory full-page interstitial.
- Account-skip success should not create warning styling; frame it as a valid deferred step.

### Error and Security States
- Wrong PIN uses inline error text under the PIN field.
- Backoff state replaces the primary button label with the remaining cooldown time, for example `Try again in 30s`.
- Recovery-key reset warnings and destructive security actions must use explicit confirmation copy and strong contrast styling.
- Windows lock or sleep return should reopen directly into the lock screen, not a transient splash.

### Keyboard Contract
- `Tab` and `Shift+Tab` move through all interactive controls in logical order.
- `Enter` activates the primary action for the current step only when validation passes.
- `Esc` does not exit onboarding. After onboarding, `Esc` may dismiss non-destructive overlays only.
- The lock screen PIN field receives focus on entry.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding |
| sm | 8px | Compact field help text and chip spacing |
| md | 16px | Default control spacing and form rhythm |
| lg | 24px | Card padding and grouped field sections |
| xl | 32px | Panel padding and shell gutters |
| 2xl | 48px | Major panel separation and empty-state spacing |
| 3xl | 64px | Page-level breathing room on desktop |

Exceptions: 44px minimum hit area for icon-only buttons and header utilities; 56px input height for PIN and primary onboarding fields

## Typography

|------|------|--------|-------------|

Use sentence case for all headings, button labels, and helper text. Reserve display text for the welcome screen headline and the lock screen household/app title only.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | #F5F1E8 | App background, onboarding canvas, lock background |
| Secondary (30%) | #E2D7C5 | Cards, shell rail, account context panel, bordered sections |
| Accent (10%) | #0F766E | Primary actions, active focus ring, progress emphasis, trusted success moments |
| Destructive | #B42318 | PIN reset warnings, destructive confirmations, irreversible security actions |

Accent reserved for: primary buttons, focused input outlines, progress labels, selected radio or checkbox controls, and the empty-dashboard import CTA. Do not use accent for secondary buttons, passive icons, or decorative backgrounds.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Start setup |
| Empty state heading | Ready for your first import |
| Empty state body | Add your first ICICI statement to create the account timeline and unlock dashboard insights. |
| Error state | We couldn't verify that PIN. Check the digits and try again. If you're locked out, use your recovery key. |
| Destructive confirmation | Reset PIN with recovery key: This will replace the current PIN and issue a new recovery key for this device. Continue only if you have access to the old data owner context. |

Microcopy rules:
- Use direct, privacy-first language. Prefer `saved on this device`, `not uploaded`, and `you can change this later`.
- Avoid consumer-fintech hype words such as `smart`, `magic`, or `instant`.
- Security confirmations must state the consequence first, then the recovery path.
